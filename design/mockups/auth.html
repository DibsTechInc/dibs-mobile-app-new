01

Why the error sits under the password

The field-level message is attached to the control it is about, so a screen reader announces it as the field's hint and a sighted client's eye does not have to travel to a banner and back.

It is deliberately the same message for a wrong password and an unknown email. The second-person alternative — "we don't have an account for that address" — is a free client-list oracle for anyone with the studio's app installed.

What the button does while working

Label stays, spinner appears to its left, control dims to 45%. It never swaps to "Signing in…" — a label that changes width makes the button jump under the thumb.

Create an account — four things, and one of them is optional

First and last name share a row because together they are one idea. Phone is marked optional in the label rather than in a hint, so the client can see it is skippable before they tap in.

Order note: the Dibs record is created BEFORE the Firebase credential. Creating the credential flips the session, and everything reacting to that flip is keyed on the Dibs userid — so the row has to exist first. Not asked for: birthday. The backend accepts it and nothing in v1 reads it; a field that buys nothing costs a client's patience.

02

Why the CTA dims instead of disappearing

A disabled control the client can still see teaches them what is left to fix. Removing it leaves them scrolling for a button that was there a second ago.

The already-a-client case

One Dibs identity spans every studio, so someone who has booked at another Dibs studio already has a record. Creating an account here just associates it, and the backend says so (code 18). That is not an error and the screen never presents it as one.

What IS surfaced: an email that already has a Firebase credential — "There's already an account with that email. Sign in instead, or reset the password."

Reset, sent, and the two session states

Reset is one field. Its confirmation replaces the form rather than appearing above it — nothing left to do on this screen means nothing left on this screen.

Copy note: the confirmation says "if there's an account" on purpose. Reporting success only for real addresses would leak the same client list the sign-in error is careful not to. The fourth frame is the state nobody designs for: a valid login whose Dibs record is missing. Every authenticated call rejects that client, so leaving them "signed in" is a dead end with no exit — it gets a real explanation and a real button.

03

The state that is usually a dead end

A Firebase credential with no dibs_user row happens: an abandoned sign-up, a credential created against the wrong project, a case-mismatched email. Every authenticated endpoint answers 403 for that client.

Most apps show a spinner forever or bounce to login, where the same credentials work and the same nothing happens. This frame names what is wrong and offers both exits.

Why the studio's email is at the bottom

It is the studio's own customerServiceEmail from their live config, not a Dibs address. To this client, the studio IS the company.

Stress test — a loud accent under the same rules

#E8442A, the "VOLT energy" case from the brief. Nothing about the composition changes; the accent still appears exactly twice, once filled and once as a link.

What this proves: the restraint is in the layout, not in the colours we happened to pick. If a hot brand colour still reads as considered here, a studio cannot break their own app by choosing badly. The hero is Carlsbad's photo purely so the only variable is the accent.

Open question for you

The heading sits on the photo in all of these. On Everyday Ballet the dancer image is high-key, so the scrim has to work hard and can read as a smudge rather than a treatment.

The alternative for that studio only: photo band with no text on it, heading below in --text. It is the same fix flagged for Home. Worth deciding once, for both surfaces, once you have seen them on a device.
